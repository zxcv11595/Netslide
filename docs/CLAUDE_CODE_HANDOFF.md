# Claude Code 전체 구현 지시서 — 햄스터 간식 배달
기준일: 2026-11-11 / 첫 웹 공개 목표: 한국 시간 2026-11-15
이 문서는 과거 꽃 성장 기획보다 우선하는 최신 요구사항이다.

## 1. 역할과 작업 방식
- Claude Code는 코드, UI, 퍼즐 데이터, 생성·검증 도구, 애니메이션, 테스트, 로컬 실행과 배포용 빌드를 맡는다.
- Codex는 생성형 이미지 제작과 별도 코드·화면 검토를 맡는다. 이미지 추가가 필요하면 요청 목록을 남기고 임시 리소스로 진행한다.
- 현재 열린 프로젝트의 AGENTS.md 등 작업 지침, 파일, Git 상태와 실행 방법부터 확인한다. 관련 없는 기존 변경은 덮어쓰지 않는다.
- 이 문서와 assets가 들어 있는 폴더는 전달용 패키지이지 자동으로 수정할 프로젝트 루트는 아니다.
- 이전 경로 D:\Github\DefenceGame은 존재 여부가 확인되지 않았다. 실제 프로젝트를 확인하고, 불명확하면 경로만 질문한다. 현재 폴더에 새 구현을 하라는 사용자 지시가 있으면 그 위치를 사용한다.
- 일상적인 구현·수정·테스트마다 승인을 반복해서 요청하지 않는다. 계획만 제시하고 멈추지 말고 구현과 검증까지 이어간다.
- 파괴적인 삭제, Git 이력 변경, 외부 공개 배포, 유료 서비스 가입·결제는 별도 지시 없이 하지 않는다.
- 모든 로컬 구현·검증·빌드를 완료한 후 외부 배포가 필요한 마지막 단계만 구체적으로 보고한다.

## 2. 목표와 기술
- 설치·가입 없는 모바일 세로형 웹 퍼즐. PC 브라우저도 지원한다.
- JavaScript 사용. TypeScript는 사용하지 않는다.
- 새 프로젝트 기본 구성: Vite + Vanilla JavaScript + HTML/CSS, 보드는 SVG.
- 기존 프로젝트가 있다면 불필요하게 재작성하지 않는다. 이미 Canvas를 쓴다면 유지할 수 있다.
- 대형 엔진이나 상태 관리 프레임워크는 추가하지 않는다.
- 순수 규칙 모듈은 DOM/렌더러와 독립적이어야 하며 Node 도구와 게임에서 같이 사용한다.
- 정적 호스팅 빌드. 첫 버전에는 계정, 클라우드 저장, 게임 서버가 없다.
- 출시 범위: 짧은 입문, 초중고 난이도, 검증된 정규 판, 별, 개인 기록, 로컬 저장, 기본 애니메이션.
- 오늘의 도전과 같은 판 공유는 핵심 완료 뒤 구현한다. 마감상 제외해야 하면 이유와 상태를 명시한다.
- 검증되지 않은 판 수량을 늘리느라 출시를 늦추지 않는다.

## 3. 콘셉트와 제외
- 가칭: 햄스터 간식 배달. 이름은 설정 한곳에서 바꿀 수 있게 한다.
- 줄을 밀어 터널을 연결해 햄스터에게 간식을 보내는 퍼즐.
- 캐릭터는 목표와 성공 연출용이다.
- 제외: 꽃/캐릭터 성장, 꾸미기, 도감/스티커 수집, 인벤토리, 재화 경제, 상점, 힌트/자동 풀이 UI, 하트/에너지, 시간 제한, 이동 초과 실패, 로그인, 온라인 순위표/실시간 대전, 구독/시즌패스.
- 완성도를 이유로 제외 기능을 임의 추가하지 않는다.

## 4. 보드와 이동 규칙
- 3×3, 4×4, 5×5 지원.
- 공급원 1개. 공급원이 있는 행과 열은 이동 불가.
- 3×3/5×5 공급원은 중앙. 4×4는 중앙 네 칸 중 스테이지 데이터로 지정.
- 가장자리 버튼으로 행/열을 한 칸 이동. 끝 타일은 반대편으로 돌아온다.
- 타일의 방향은 회전하지 않는다. 목표 타일도 해당 줄과 함께 이동한다.
- 직접 회전, 드래그 조작, 별도 벽 규칙은 첫 버전에 넣지 않는다.
- 잠긴 줄과 이유를 시각적으로 보여준다.
- 이동 가능한 줄은 양방향 조작을 모두 제공한다.

## 5. 연결 규칙
- 인접한 두 타일의 열린 방향이 서로 마주 볼 때만 연결.
- 이동의 순환과 경로 연결은 별개다. 보드 반대편 가장자리끼리는 연결되지 않는다.
- 공급원부터 BFS로 도달 상태를 계산한다.
- 일반 수로는 열린 포트 사이로 흐름을 전달한다.
- 일반 목표는 한쪽 입구를 가진 끝 타일.
- 방향 타일은 지정 입구로 들어온 흐름만 지정 출구로 전달한다. 입구/출구를 명시하고 화살표로 표시한다.
- 포트/방향성 때문에 도달 상태가 달라질 수 있으면 탐색 상태를 입구 방향까지 포함해 정의한다. 단순 방문 여부로 유효 경로를 누락하지 않는다.
- 이동 직후 현재 배치 전체에서 연결을 재계산한다. 이전에 연결한 목표도 끊기면 미연결이다.
- 모든 필수 목표가 동시에 연결되어야 기본 클리어 가능.
- 보너스는 필수를 모두 유지하면서 모든 보너스도 동시에 연결되어야 한다.

규칙 함수 기본 분리:
1) shiftBoard: 합법성 검사와 순환 이동.
2) evaluateConnections: 현재 흐름/목표 연결 상태.
3) evaluateResult: 필수·보너스 달성과 별.
게임과 생성·검증 도구가 동일한 함수를 호출해야 한다.
화면 코드가 별도의 연결/별 규칙을 중복 구현하지 않는다.

## 6. 완료·별·되돌리기
- 필수 달성 시 완료 버튼 활성화. 자동으로 결과 화면에 넘기지 않는다.
- 완료하지 않고 추가 조작해 보너스를 노릴 수 있다.
- 현재 배치가 조건에서 벗어나면 완료 가능 상태도 다시 계산한다.
- 완료 버튼을 눌러 확정할 때만 기록과 다음 판 해금을 처리한다.
- 별 1개로 완료해도 다음 판을 연다.
- 보너스 있는 판: 1별=필수, 2별=필수+모든 보너스, 3별=2별 조건+목표 이동 수 이내.
- 보너스 없는 일반 판: 1별=필수, 2별/3별=데이터로 정한 두 이동 수 기준. 3별 기준이 더 엄격해야 한다.
- 입문은 별 없이 완료 표시 가능.
- 이동 한 칸=1수. 무효/잠긴 줄 입력은 0수.
- 무제한 되돌리기: 직전 배치와 이동 수 함께 복원.
- 되돌린 후 새 이동은 이전 미래 이력을 폐기. 재시작은 시작 배치와 0수.
- 기록은 총 실험 횟수가 아니라 최종 풀이 길이.
- 최고 별은 낮아지지 않는다. 기본 최소 이동 기록과 보너스 포함 최소 이동 기록을 구분한다.
- 최단 증명이 없는 수는 '목표 이동 수'라고 표시한다.

## 7. 진행과 난이도
- 입문 2~3판: 3×3으로 줄 이동, 순환, 연결을 직접 익힌다.
- 입문 후 초급/중급/고급을 모두 선택 가능.
- 난이도 내에서는 앞 판 기본 클리어로 다음 판 해금.
- 초급 전체를 깨야 중급에 들어가는 방식은 금지.
- 초급: 3×3과 단순 4×4. 중급: 4×4 중심. 고급: 복잡한 4×4와 5×5.
- 격자 크기만으로 난이도를 판정하지 않는다.
- 35판은 필수 아님. 참고 배분은 3×3 5개 / 4×4 15개 / 5×5 15개.
- 수량보다 풀이 검증, 서로 다른 판단, 적절한 난이도를 우선.
- 스테이지 ID, 난이도, 표시 순서를 분리한다.
- 간단한 난이도 탭/버튼과 스테이지 목록. 대형 월드맵은 만들지 않는다.
- 없는 콘텐츠의 빈 잠금 노드를 대량 노출하지 않는다.

## 8. 생성·검증 도구
- 출시 판은 개발 중 미리 생성·검증해 데이터 파일로 내보낸다. 런타임에서 무거운 해답 탐색 금지.
- 목표가 모두 연결된 정답 배치 → 합법 이동 셔플 → 역순 해답 보관 → 공통 규칙으로 재생 확인 → 풀이 탐색 → 중복/과도한 쉬움 제거 → 잠정 난이도 지정.
- N번 셔플은 최소 N수 증명이 아니다.
- 현재 판의 연결 BFS와 판 상태 공간의 풀이 BFS를 구분.
- 탐색 시간/상태 수 제한. 제한 초과는 미해결/미증명이지 해답 없음이 아니다.
- 큰 판의 무제한 BFS 금지. 발견한 해답과 최단 증명을 구분.
- 기본 목표와 보너스 포함 목표를 각각 검증.
- 3별 기준에는 실제 달성 가능한 보너스 포함 해답이 있어야 한다.
- 회전/반사 중복 제거는 공급원·잠금·방향성을 보존하는 변환에만 적용.
- 풀이 기록은 사용자에게 노출하는 판 JSON과 분리해 개발용 검증 자료로 둔다. 클라이언트의 해답 비밀 유지나 치트 방지를 보장하지 않는다.
- 판별 보드 크기, 기본/보너스 해답 길이, 최단 증명 여부, 탐색량, 제외 이유를 보고서로 남긴다.

- 참조 시안의 퍼즐 배치는 해답/연결 검증을 하지 않았다. 타일 배치와 상태 숫자를 그대로 복제하지 않는다.
- 크림 배경, 주황 포인트, 짙은 갈색 선과 글씨의 따뜻한 2D 스타일.
- 배경, 수로, 타일, 버튼, 별, 잠금은 코드로 만든다.
- 전체 시안 이미지를 게임 화면 배경으로 붙이고 클릭 영역만 얹는 구현 금지.
- 작은 목표는 코드 얼굴 아이콘을 쓰거나 제공 이미지를 적절히 표시. 전체 몸통을 작게 줄여 판을 복잡하게 만들지 않는다.
- 제공 파일은 프로젝트의 public/assets 등 적절한 위치로 복사하고 이름/경로를 한곳에서 관리.
- 원본 비율 유지. 상태 전환 시 같은 고정 프레임과 발 기준선 사용. 이미지 크기 차이를 CSS로 왜곡하지 않는다.
- 게임 표시 크기에 맞춘 파생 파일이 필요하면 비파괴 방식으로 만들고 원본을 보관.
- 이미지 누락 시 대체 표시.
- 보드가 화면의 중심. 큰 캐릭터 때문에 5×5 조작 영역이 작아지지 않게 한다.
- 필수/보너스/방향은 색 외에 아이콘·모양으로도 구분.
- 모바일 320/360/390px 폭과 PC에서 확인. 버튼은 누르기 쉬운 크기, 필요하면 외곽 hit area 확장.
- 안전 영역, 브라우저 상하단 크기 변경, 페이지 확대를 고려.
- 캐릭터 이름, 수치, 버튼 글씨를 이미지 안에 굽지 않는다.

## 10. 애니메이션 구현
실제 프레임 애니메이션이 아니라 두 정적 이미지 + CSS transform/opacity + SVG 경로를 사용한다.
아래 수치는 시작값이며 실제 조작감에 맞게 소폭 조정할 수 있다.

대기:
- hamster-idle 사용.
- 발 쪽 transform-origin, 2.4~3.2초 주기로 scaleY 1~1.015, translateY 0~-2px 정도의 미세한 숨쉬기.
- 큰 흔들림이나 계속 튀는 동작은 금지.

줄 이동:
- 140~200ms 부드러운 한 칸 이동.
- 보드 경계에서 순환하는 타일은 임시 복제해 양끝 이동을 연출하고 클리핑한다.
- 이동 중 보드 조작/완료/되돌리기/재시작은 잠시 잠가 논리 상태와 렌더링이 어긋나지 않게 한다.
- transitionend 누락에도 잠금이 풀릴 fallback과 취소 처리를 둔다.
- 하나의 확정된 다음 배치만 사용. 화면용 복제 타일은 규칙/저장에 포함하지 않는다.
- 이동이 확정된 뒤 새 배치 기준으로 흐름 표시. 움직이는 동안 새 흐름이 고정된 옛 타일 위에 보이지 않도록 한다.

흐름:
- 공급원에서 가까운 경로부터 30~50ms 간격으로 활성화하되 전체 대기는 약 350ms 이내.
- 순환 경로에서도 무한 효과나 중복 펄스가 생기지 않게 한다.
- 긴 연출 때문에 다음 입력을 불필요하게 막지 않는다.
- 새 이동이 들어오면 이전 장식 효과를 취소하고 최신 상태를 보여준다.
- 실제 판정은 시각 효과 완료를 기다리지 않는다.

완료:
- 퍼즐 중에는 간식이 도달 가능한 상태를 표시할 뿐 실제로 계속 먹이지 않는다.
- 완료 버튼에서 배치/별/기록을 한 번 확정하고, 실제 연결 경로를 따라 간식 전달을 약 400~650ms 보여준다.
- 경로는 연결 판정에서 얻은 유효 경로를 사용. 보드와 무관한 가짜 직선 배달 금지.
- 경로가 여러 개면 목표별 대표 경로를 선택하고 과도한 중첩은 줄인다.
- 그 뒤 대기→성공 이미지를 100~150ms 정도로 전환.
- 성공 햄스터가 6~10px 정도 짧게 점프/착지. 약 250~350ms.
- 별은 80~120ms 간격으로 실제 획득 수만큼 등장, 작은 scale 효과.
- 성공 연출은 총 약 1초 안팎. 다음 판 조작을 오래 기다리게 하지 않는다.
- 더블 탭으로 중복 저장/해금하지 않는다. 중단되더라도 결과 기록은 유실하지 않는다.
- 먹는 모션/걷는 모션이 있다고 표현하지 않는다. 실제 씹기는 후속 아트가 필요한 별도 작업이다.

설정/수명:
- prefers-reduced-motion이면 이동·점프를 제거/단축하고 상태는 즉시 확인 가능.
- 화면 전환, 재시작, 탭 비활성화에서 타이머/RAF/임시 DOM을 정리.
- 게임 상태, 렌더 전환, 장식 효과를 분리.
- 광고 중 모든 게임 입력과 오디오를 일시 정지. 복귀 시 사용자의 기존 설정을 보존.
- 소리는 첫 버전 필수 아님. 제공하지 않은 사운드 자산을 임의 외부 수집하지 않는다.

## 11. 오늘의 도전과 공유
- 핵심 완료 후 구현.
- 검증된 별도 일일 판 목록을 한국 시간 Asia/Seoul 날짜에 대응.
- 동일 날짜에는 모두 동일한 배치/목표/별 기준.
- 일반 스테이지 플레이에는 일일 횟수 제한이 없다.
- 링크는 콘텐츠 버전+판 ID(일일 판은 날짜/ID 포함)로 재현하고 과거 링크도 유지.
- 판/규칙 수정 시 기존 링크를 다른 판으로 조용히 바꾸지 않는다.
- 신규 안내 뒤 원래 공유 판으로 복귀.
- 링크 파라미터 검증, 잘못된 ID와 구버전 처리.
- 결과 공유: 별, 이동 수, 보너스 달성 여부, 같은 판 링크. 완료 배치는 기본 공유에 넣지 않는다.
- Web Share API 지원 시 사용, 미지원이면 복사. 취소/실패를 성공 처리하지 않는다.
- 서버 없는 기록은 공식 순위/치트 방지 기능이 아니다.

## 12. 저장
- 버전이 있는 localStorage 데이터.
- 입문, 해금, 최고 별, 기본/보너스 최고 이동 수, 현재 판/수/되돌리기 이력, 일일 기록, 실제 제공 설정.
- JSON 손상/저장 실패/구버전 데이터로 전체 게임이 멈추지 않게 한다.
- 저장 불가면 메모리로 플레이하고 짧게 안내.
- 브라우저 데이터 삭제/기기 변경 시 로컬 기록 소실 가능 안내.
- 콘텐츠 버전이 다른 판 기록을 섞지 않는다.
- 구매 권한을 이 저장 시스템에 임의 추가하지 않는다.

## 13. 광고와 수익화 — 이번 구현 범위
분류:
- 현재: 무료 플레이 + 판 사이 전면 광고 후보.
- 제외: 보상형 광고, 힌트 판매, 에너지 판매, 구독.
- 광고 제거는 비소모성 결제 상품이며 인앱결제 후속 작업이다. 이번에는 판매 버튼/가격/가짜 구매 흐름을 만들지 않는다.
- 웹 광고 제거 판매도 구매자 식별과 복원 설계가 필요하므로 이번 범위에서 제외.
- 앱 확장 시 전면 광고 제거 1회 결제, 구매 확인/취소/환불/복원은 별도 설계.
- 제거 범위를 모호하게 '모든 광고 제거'로 미리 약속하지 않는다.

배포별 구분:
- 일반 웹: 웹용 광고 사업자/SDK와 승인 상태를 확인한 뒤 연동.
- 게임 포털: 해당 플랫폼의 광고 SDK/정책을 따르고 다른 광고망을 중복 추가하지 않는다.
- 앱: 네이티브 광고·스토어 결제 연동은 별도 작업. 웹에 AdMob 네이티브 SDK를 그대로 붙이지 않는다.
- 사업자/계정/배포 경로가 미정이면 SDK 삽입, ID 추정, 운영 광고 요청, 외부 추적 스크립트 삽입을 하지 않는다.
- 사용자에게 필요한 사업자 결정사항과 공식 연동 문서 경로를 인계에 남긴다.
- 승인/심사 때문에 게임의 이번 주 공개 자체를 지연시키지 않는다.

지금 만들 것:
- 작은 광고 어댑터와 판 사이 광고 기회.
- 광고 비활성 기본값. 설정이 없으면 no-op 즉시 통과.
- 상태: 준비 안 됨 / 요청 / 실제 표시 중 / 종료·실패를 구분.
- 광고가 실제로 표시될 때만 게임 입력/오디오 일시 정지.
- 광고 종료·거절·재고 없음·SDK 오류는 정상적으로 다음 판 진행.
- 하나의 광고만 요청/표시. 다음 판 더블 클릭의 중복 요청·중복 이동 차단.
- 게임 진행 상태를 먼저 안전하게 확정/저장.
- 제공자 API의 공식 완료·실패 콜백을 따라 대기 상태 복구.
- SDK가 아직 로딩 중이거나 요청이 종료되지 않는 상황은 어댑터 경계에서 처리.
- 실제 광고 표시 중 임의 타임아웃으로 뒤의 게임을 재개하지 않는다.
- 취소되거나 오래된 콜백이 다른 화면을 이동시키지 않게 한다.
- 광고 실패를 성공 노출로 세지 않는다.
- 개발용 모의 어댑터에서 성공/재고 없음/실패를 시험하되 운영 빌드에 가짜 광고 화면은 노출하지 않는다.
- 운영 SDK 연동 때는 공식 테스트 모드 사용, 실제 광고 클릭 테스트 금지.

광고 기회:
- 첫 방문 안내/입문/초반 플레이는 제외.
- 완료 결과 확인 후 '다음 스테이지' 전환에서만 후보.
- 플레이 중, 페이지 최초 로딩, 되돌리기, 재시작, 공유 링크 첫 진입, 별 재도전에는 넣지 않는다.
- 기록/별 조건을 광고로 유리하게 바꾸지 않는다.
- 초기 실험값: 일반 판 3개 이상 완료 + 이전 실제 노출 이후 5분 이상 경과한 경우.
- 첫 실제 노출 전에도 입문 이후 일반 플레이 5분 이상 필요.
- 재도전 반복으로 노출 횟수 조건을 채우지 않도록 서로 다른 정규 판 완료를 기준으로 한다.
- 위 숫자는 최적값/정책 보장이 아니라 설정 가능한 시작값이다.
- 사업자·포털의 공식 빈도 제한이 있으면 함께 적용하고 더 엄격한 쪽을 따른다.
- 재고 없음/실패 시 같은 전환에서 연속 재요청하지 않는다.
- 광고가 준비되지 않았다고 '광고 준비 중' 화면으로 붙잡지 않는다.

## 14. 검증
자동 검증:
- 이동+역이동 원복, N칸 줄 N회 이동 원복, 잠긴 줄, 방향 유지.
- 타일 수/ID 보존, 공급원 고정, 반대편 경계 연결 금지.
- 포트 맞물림, 방향성, 순환 경로 종료.
- 필수·보너스 동시 달성, 별 수치 경계.
- 되돌리기/재시작/이력 분기.
- 모든 출시 판의 해답 재생과 별 목표 달성 가능성.
- 저장/해금/최고 기록 유지/손상 데이터.
- 링크 재현/잘못된 버전·ID, 일일 날짜 경계.
- 애니메이션 중 연타/취소/재시작 시 상태 일치.
- 광고 no-op, 미준비, 표시·종료, 재고 없음, 오류, 중복 클릭, 늦은 콜백.
- 광고 조건 미충족/충족, 실패 후 연속 재요청 방지, 종료 후 정상 복귀.

실제 확인:
- 모바일/PC 첫 진입→입문→일반→1별 완료→다음 판.
- 보너스를 위해 계속 조작.
- 5×5의 버튼 크기와 가독성.
- 새로고침 복원, 이미지 누락, 동작 줄이기.
- 같은 링크의 동일 배치, 광고 비활성일 때 정상 플레이.
- 운영 빌드 성공과 정적 호스팅 하위 경로의 이미지/링크.
- 자동 테스트와 실제 브라우저 확인, 미검증 항목을 구분.
- 실행하지 않은 기기/브라우저/광고망은 확인했다고 쓰지 않는다.

## 15. 권장 구조와 순서
권장 경계:
core/ 순수 규칙
game/ 현재 판·이력·완료
ui/ 화면·입력·애니메이션
data/ 검증된 판
storage/ 로컬 저장
ads/ 작은 광고 어댑터
tools/ 생성·검증

순서:
1) 프로젝트 조사/실행 → 규칙/검증
2) 소수 판으로 전체 흐름 → 모바일 UI/제공 아트
3) 별/진행/저장 → 생성/검증/콘텐츠
4) 애니메이션 → 일일/공유 → 광고 연결부
5) 전체 확인/수정/빌드
- 마감이 위험하면 기능·수량을 줄이고 정확성·저장·모바일 확인은 유지한다.
- 미완성 기능 버튼은 숨기고 누락 사항을 보고한다.
- 과도한 범용 프레임워크나 플러그인 구조는 만들지 않는다.
